## 1. What I used an AI assistant for, and what I did myself
I used Claude (Claude Code) to help me diagnose two real infrastructure/model issues along the way (a stuck Ollama request after an interrupted session, and a `qwen3:8b` reasoning-mode bug causing runaway output) and help designing how the agenets should tal to each other on the agent.
What I did myself: wrote most of the code across all four parts: the HTML/CSS/JS course form, the Dockerfile, the AWS ECS deployment walkthrough, `agents_demo.py` (Planner/Reviewer/Finalizer), `run_nondeterminism.py`, `src/model_client.py`, and `hw1_client.py`. Every live terminal interaction that produced a real deliverable was typed by me personally, in my own terminal, the Part 2 agent conversation, the Part 3 non-determinism runs, and the Part 4 chat session. I made the domain and schema decisions (Course entity for the campus catalogue domain), chose which local model to use, decided when a result looked wrong and needed investigating rather than accepting it at face value.


## 2. Two distinct uses of the Ollama model in this project

**Agentic tagging pipeline (Parts 2 & 3).** `qwen3:8b` runs as both the Planner and Reviewer agents in `agents_demo.py`, called through `ChatOllama` with `format="json"` to force strict JSON output. Given only a title and content, the Planner drafts exactly 3 topical tags and a summary of at most 25 words with no domain-specific hardcoding, and the Reviewer independently re-checks that draft against the original content, either approving it unchanged or correcting it. The identical pipeline was then re-run unchanged 40 times in `run_nondeterminism.py` -- 20 times at temperature 0.7 and 20 at temperature 0.0 -- to measure how much the model's output actually varies run-to-run at each setting.

*How I verified this worked:* I ran it on the assigned Course domain input, then deliberately fed it an unrelated grocery-recall input to confirm the tags/summary were genuinely derived from the content rather than hardcoded domain keywords -- both produced correctly domain-specific tags. Across single runs and the full 40-run sweep, the output was always valid JSON with exactly 3 tags and a summary at or under 25 words, so no fix was needed here; this pipeline worked correctly from the first implementation.

**Interactive code-review assistant (Part 4).** The same model is used differently in `hw1_client.py`: instead of a single structured JSON task, it drives a multi-turn conversational chat session through `src/model_client.py`, with `AGENT.md` set as its system prompt instructing it to act as a code reviewer that responds only in bullet points. Across a 5-turn conversation, the model reviewed several code snippets and answered a follow-up summary question, with `ModelClient` tracking real per-turn and cumulative input/output token usage for every call.

*How I detected problems here:* two separate issues surfaced. First, on the very first turn of two different sessions, the model ignored `AGENT.md` entirely and produced a rambling, unformatted 8,000-12,000+ token response -- caught immediately because every other turn stayed under 100 output tokens and followed the bullet format. Second, when the demo used bare arithmetic snippets (`def add(a, b): return a + b`, `def multiply(a, b): return a * b`), the model repeatedly invented division-related bugs that didn't exist -- caught by manually checking each flagged claim against the actual code, since none of those functions contained a division operator at all.

*What I changed and why it works now:* for the runaway-response issue, I set `reasoning=False` on `ChatOllama` in `src/model_client.py` to disable `qwen3`'s internal "thinking" mode, and verified the fix by re-running the exact prompt that had failed -- it returned a clean 24-token single bullet instead of 8,000+ tokens of rambling. For the division hallucination, I didn't find a code-level fix; instead I changed the demo's example inputs from synthetic arithmetic snippets to realistic code-review scenarios (list operations, a hardcoded secret, a loop-style question), and re-ran the full 5-turn conversation, which produced accurate, correctly formatted reviews on every turn with no hallucinations.

### A related, secondary finding worth noting

Separately from the above, the local LLM under test (`qwen3:8b`) itself produced genuinely wrong output on several occasions, independent of anything Claude wrote: it hallucinated division-related bugs in code that contained no division operator at all (reviewing `def add(a, b): return a + b` and `def multiply(a, b): return a * b`), and on two separate sessions produced a runaway 8,000-12,000+ token unformatted response instead of following the `AGENT.md` bullet-only instruction. I detected the first by manually checking each hallucinated claim against the actual code (none of the flagged "division" issues existed), and the second simply by the response ignoring the required output format. The runaway-response issue was fixed by explicitly setting `reasoning=False` in `src/model_client.py` (verified by re-running the identical failing prompt, which then returned a clean single bullet); the division hallucination was worked around, not fixed, by switching the demo's example inputs away from bare arithmetic snippets to more realistic code-review scenarios, which reliably produced accurate reviews on every subsequent run. Both are documented in detail in `report.pdf`'s Part 4 section.
